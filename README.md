# Тестовое задание — AI Lead

## Что нужно сделать

Вы реализовываете небольшую версию **AI Admin** — чатбота, который общается с клиентами и помогает им создать или отменить запись в салон.
Ваша задача - дописать извлечение интента из сообщения пользователя с помощью LLM и обработку этого интента.  
Можно и нужно пользоваться Claude, Codex, etc.

### Как должен работать диалог

- **Запись (booking)**. У клиента нужно собрать три поля: услугу, дату и время. Если чего-то из них нет в реплике — задать уточняющий вопрос. Когда все три поля собраны, попытаться создать запись через `booking_api`. Если слот занят — сообщить пользователю и попросить выбрать другие дату/время.
- **Отмена (cancellation)**. Обязательно нужны дата и время записи; услуга опциональна — если клиент её указал, ассистент проверит, что она совпадает с фактической записью на этот слот. По дате+времени ищем запись через `find_booking`, и если нашли (с совпадающей или не заданной услугой) — отменяем.
- **Смена интента**. В любой момент клиент может передумать и одной репликой переключиться с booking на cancellation или наоборот. Ассистент должен это поймать и продолжить диалог уже по новому интенту.

### Реализовать в `ai_admin/implement_this/`

1. **`extractor.extract_user_intent`** — извлечение интента из реплики пользователя с помощью LLM в `ExtractedIntent`.
   - Фреймворк на ваш выбор: pydantic-ai / langchain / другой.
   - Рекомендуемая модель — `gpt-4.1-mini`.
2. **Логику обработки интента** в `orchestrator.py` — пять хелперов:
   1. `update_state`
   2. `decide_next_step`
   3. `execute_action`
   4. `apply_action_result`
   5. `generate_response`

   У каждого в docstring уже описана ожидаемая логика.

`process_message` в `orchestrator.py` уже сшит — трогать его не надо. Цель — наполнить хелперы так, чтобы pipeline собирался:
- разобрать intent
- обновить state
- решить что сделать в зависимости от интента и стейта
- дёрнуть метод из `booking_api` или задать уточняющий вопрос
- сформировать ответ (без LLM, шаблоном)

## Booking API

Эти функции эмулируют CRM, хранят данные в памяти процесса. Используйте в
`execute_action`, их менять не нужно:

| Метод | Делает |
|---|---|
| `create_booking(service, when)` | Создаёт запись. Если слот занят — возвращает `BookingResult` c `needs_clarification=True`. |
| `find_booking(when, service=None)` | Возвращает `BookingSearchResult` со статусом `found` / `not_found` / `service_mismatch`. |
| `cancel_booking(booking_id)` | Отменяет запись по id. |

## Success criteria

В `cases.py` лежат 8 sample-кейсов. Реализация должна их проходить.

**Можно и нужно дописывать свои кейсы** — особенно по сценариям, которые
вы заметите в коде, но которых нет в стартовом наборе. Структура
`Case` + `Expected` простая, добавляйте по аналогии. Проверка будет запущена на расширенном кол-ве тестовых кейсов + на тех, которые вы добавили (aka Kaggle-style).
